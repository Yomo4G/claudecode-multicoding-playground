# Coding Standards

This rule defines coding standards for all product code.
Company standards take precedence over team standards.

## Applicability

This rule applies to the following agents:
implementer, reviewer, refactorer, verifier

## Priority Resolution

会社基準（Company Standards）はチーム規約（Team Standards）に優先する。
両者が矛盾する場合、会社基準に従う。

## Company Standards（会社基準）

Source: https://zozo.atlassian.net/wiki/spaces/CENTRAL/pages/23724347/-+Frontend
Updated: 2024-10-09 (Author: Kenji Gonnokami)

各ルールの強度レベル:
- MUST: 必須。違反は許容しない
- RECOMMENDED: 推奨。合理的な理由がある場合のみ省略可
- MUST NOT: 禁止。違反は許容しない

### 全般

#### C1: コーディング規約に従う（MUST）

- プロジェクトで使用するコーディング規約を定義し、従う
- コーディング規約をドキュメントとして残す
- 開発チーム内で同意を取る
- 継続的にメンテナンスする
- linter を導入して規約への準拠を自動チェックする

#### C2: コードレビューを行う（MUST）

- 他者によるコードレビューを必ず行う

#### C3: 自動テストを実施する（MUST）

- 自動的に単体テスト、linter が実行される仕組みを導入する
- テストに必要な前処理・後処理すべてを自動化する
- リリース前には必ず自動テストを実施し、合格を確認する

#### C4: プロダクト固有の用語を定義する（RECOMMENDED）

- プロダクト/プロジェクトで使用する用語を統一して定義する
- クラス名、変数名、メソッド名の命名にも統一された用語を使用する

### 開発環境

#### C5: GitHub でコードを管理する（MUST）

- サービスのために記述したコードは必ず GitHub で管理する
- サービスへ反映されている状況と GitHub 上のコードに乖離がないことを保証する

#### C6: 文字コードは UTF-8 を用いる（MUST）

- HTML, CSS, JavaScript などソースコードの文字コードは必ず UTF-8 を用いる

#### C7: パッケージの依存関係を管理する（MUST）

- npm 等のパッケージ管理ツールで依存関係を管理する
- ロックファイル（package-lock.json / pnpm-lock.yaml 等）も
  GitHub で管理する

#### C8: TypeScript を導入する（RECOMMENDED）

- SPA 開発など JavaScript の規模が大きくなる場合は
  TypeScript を導入する
- 静的型チェックと IDE 補完により開発効率を維持する

### デザイン

#### C9: レスポンシブデザインを用いる（RECOMMENDED）

- 表示環境に応じて適切にレイアウトが変わるようにする
- WebView や特定用途のページは該当環境のみの考慮でよい

#### C10: デザインに忠実にコーディングを行う（RECOMMENDED）

- デザインデータに忠実なコーディングを行う
- 再現しきれない要素はデザイナー確認の上で許容する

#### C11: アクセシビリティを考慮する（RECOMMENDED）

- JIS X 8341-3:2016 の規格に則る実装を可能な範囲で行う

### パフォーマンス

#### C12: ソースコードの minify を行う（RECOMMENDED）

- HTML, CSS, JavaScript のソースコードは minify して配信する
- ライセンス表記部分は minify 対象外

#### C13: 画像の最適化を行う（RECOMMENDED）

- 拡張子に応じた画像の可逆圧縮を行う
- 表示範囲外の画像・動画は遅延読み込みを行う
- srcset 属性でデバイス解像度に応じた画像を配信する

#### C14: パフォーマンス計測を行う（RECOMMENDED）

- Lighthouse や PageSpeed Insights 等のツールで計測し、
  スコアの向上に努める

### セキュリティ

#### C15: 秘密情報を git にコミットしない（MUST NOT）

- 秘密情報の git へのコミットを禁止する

#### C16: 脆弱性対策を行う（MUST）

- セキュリティチェックリストに基づき脆弱性対策を行う

#### C17: セキュアなデータの保存制限（MUST NOT）

- セキュアなデータを JavaScript 経由で Cookie や
  Web Storage に保存することを禁止する
- セキュアなデータは HTTP-Only および Secure 属性が
  付与された Cookie に保存する

#### C18: セキュリティアップデートに速やかに対応する（MUST）

- ライブラリのセキュリティアップデートの有無を自動検知する
- 検知されたアラートへの対応を速やかに行う

#### C19: 定期的なアップデートを行う（RECOMMENDED）

- 言語・ライブラリなどの実行環境を定期的にアップデートする
- バージョン番号が離れるほどコストが上がるため、
  毎月・四半期・半年などの頻度で実施する

### リリース

#### C20: QA を実施する（MUST）

- リリースの際にはデザイナーチームへのデザイン確認、
  QA チームによる QA を事前に済ませる

#### C21: ステージング環境で動作確認を行う（MUST）

- 本番環境に反映する前に、必ずステージング環境で動作確認を行う

#### C22: 段階的なリリースを行う（MUST）

- 段階的なリリースを行える仕組みを構築する
- 一部のユーザーに先行リリースし、徐々に割合を上げる
- 事業都合による一斉公開やユーザー影響のないシステムは省略可

#### C23: 自動デプロイを実施する（MUST）

- デプロイを自動化する仕組みを導入する
- 自動・手動問わずデプロイ後の動作確認を行う

### ログ

#### C24: ユーザー行動ログを取得する（RECOMMENDED）

- 各ページのアクセス数などを取得する

#### C25: パフォーマンスログを取得する（RECOMMENDED）

- ページの表示速度などを取得する

#### C26: JavaScript エラーログを取得する（RECOMMENDED）

- ランタイムエラーを取得する

### 運用

#### C27: 本番オペレーションを自動化する（MUST）

- 日常的に発生する本番運用作業をツール化する
- フールプルーフ機構を盛り込む
  （デフォルト dry run、明示的な --apply オプション等）
- デフォルトの環境を開発環境とし、
  本番環境は明示的なオプション指定を必須にする

#### C28: OSSライセンスの表記・更新をする（MUST）

- 利用している OSS のライセンスに基づき適切な表記を
  JavaScript や CSS のコード中に含める

## Team Standards（チーム規約）

Sources:
- Google TypeScript Style Guide (https://google.github.io/styleguide/tsguide.html)
- Google JavaScript Style Guide (https://google.github.io/styleguide/jsguide.html)
- Google HTML/CSS Style Guide (https://google.github.io/styleguide/htmlcssguide.html)

### TypeScript / JavaScript

#### T1: 命名規則

- 変数・関数・メソッド・プロパティは lowerCamelCase を使用する
- クラス・インターフェース・型・列挙型は UpperCamelCase を使用する
- グローバル定数と列挙値は CONSTANT_CASE を使用する
- 識別子の先頭・末尾にアンダースコアを使用しない
- 略語は単語として扱う（HTTP → Http）
- 省略形や曖昧な短縮形を避け、説明的な名前を使用する

#### T2: 変数宣言

- `var` の使用は禁止。`const` をデフォルトとし、
  再代入が必要な場合のみ `let` を使用する
- 1 つの宣言につき 1 つの変数のみ宣言する
- 変数は最初に使用される地点の近くで宣言する

#### T3: 型の使用

- `any` 型の使用を避け、必要に応じて `unknown` を使用する
- オブジェクト型宣言ではインターフェースを優先する
- 型エイリアスはプリミティブ・ユニオン・タプル・複雑な式に使用する
- 単純な配列は `T[]` 構文を使用し、
  複雑な型には `Array<T>` を使用する
- 型アサーションには `as Foo` を使用し、
  `<Foo>` 角括弧構文は避ける
- Non-Null アサーション `!` は慎重に使用し、
  安全である理由をコメントで説明する

#### T4: 関数

- トップレベルの名前付き関数は関数宣言を優先する
- ネストされた関数やコールバックではアロー関数を優先する
- `arguments` オブジェクトの代わりに Rest パラメータを使用する
- アロー関数の簡潔本体は戻り値が使用される場合のみ使用する

#### T5: インポート・エクスポート

- 名前付きエクスポートのみを使用し、
  デフォルトエクスポートを避ける
- 同じプロジェクト内では相対インポートを優先する
- モジュール内で使用されない記号はエクスポートしない
- 同じファイルを複数回インポートしない

#### T6: 制御構造

- `if`・`for`・`while` は常に中括弧付きブロックを使用する
- 三重等号 `===` と `!==` を使用し、二重等号は避ける
- `for-in` はオブジェクトのみに使用し、
  配列には `for-of` を使用する
- switch 文には必ず `default` ケースを含める
- 空の catch ブロックには正当な理由をコメントで説明する

#### T7: 文字列

- 文字列リテラルはシングルクォートを使用する
- 複雑な文字列連結の代わりにテンプレートリテラルを使用する

#### T8: クラス設計

- 再割り当てされないプロパティには `readonly` を付与する
- パラメータプロパティを活用してコンストラクタを簡潔にする
- 静的メソッドのコンテナとしてクラスを使わず、
  個別の関数をエクスポートする
- プロトタイプを直接操作しない

#### T9: 禁止パターン

- `eval` および `Function(...string)` コンストラクタの使用禁止
- 組み込みオブジェクトの prototype 変更禁止
- プリミティブ型のラッパーオブジェクトに `new` を使用しない
- `Array()` コンストラクタの代わりにリテラル `[]` を使用する
- `Object()` コンストラクタの代わりにリテラル `{}` を使用する

#### T10: Null・Undefined の処理

- オプションフィールド・パラメータは `?` 構文を優先する
- Null チェック時は通常 `===` を使用する
- `|null` や `|undefined` を型エイリアスに含めず、
  使用箇所で明示する

### HTML / CSS

#### T11: HTML ルール

- セマンティックな要素を目的に応じて使用する
- マルチメディア要素に代替コンテンツを提供する
- 構造・プレゼンテーション・動作を分離する
- スタイルシートとスクリプトの `type` 属性を省略する
- 属性値はダブルクォーテーションで囲む

#### T12: CSS ルール

- 意味的で汎用的なクラス名を使用する
- クラス名の単語をハイフンで区切る
- ID セレクタの使用を避ける
- ショートハンドプロパティを可能な限り使用する
- `!important` 宣言の使用を避ける
- 宣言をアルファベット順に並べる

### 共通

#### T13: フォーマット

- インデントは 2 スペースで統一する
- 末尾の空白を削除する
- UTF-8 エンコーディングを使用する
- すべてのステートメントをセミコロンで終了する
- コード全体で一貫性を保つ

#### T14: エラーハンドリング

- 常に `Error` またはそのサブクラスをスローする
- 文字列やその他のオブジェクトをスローしない
- `new` キーワードでエラーを構築する

## Implementer Obligations

- コード生成時に該当するルールを遵守する
- 会社基準とチーム規約が矛盾する場合は会社基準に従う
- 判断に迷う場合は、より厳格なルールに従う

## Reviewer Obligations

- レビュー時にすべての該当ルールを検証する
- 違反を発見した場合、ルール番号（C1, T3 等）を引用して報告する
- 報告形式:
  - Standard: {C1 | T3 | T9 等}
  - Location: {file}:{line}
  - Description: 問題の説明
  - Recommendation: 修正方針
